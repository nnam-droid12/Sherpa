# Decisions

A running log of technical choices and where the live docs differed from the original plan.

| # | Date | Decision | Why |
|---|------|----------|-----|
| 1 | 2026-10-22 | Gemini runs on Gemini Enterprise Agent Platform (Vertex AI) via the `google-genai` SDK in Vertex mode, authenticated with Application Default Credentials. No API keys. | Keyless auth with a least-privilege service account on Cloud Run. |
| 2 | 2026-10-22 | Model `gemini-3.8-flash`, location `global`. | The Vertex computer-use docs list Gemini 3.8 Flash as supported and show REST endpoints under `locations/global`. |
| 3 | 2026-10-22 | Computer use also runs on `gemini-3.8-flash` (`ENVIRONMENT_BROWSER`). | Listed as supported in the Vertex computer-use docs. Coordinates are on a 0–999 grid and are scaled to the viewport. The model id is configurable via `SHERPA_COMPUTER_USE_MODEL`. |
| 4 | 2026-10-22 | Web → agent auth uses a shared `X-Sherpa-Key` header stored in Secret Manager. | Simpler than IAM-authenticated calls from a Next.js server, and the key never reaches the browser because the console proxies through its own server routes. |
| 5 | 2026-10-22 | Demo stores live in their own public repos (`sherpa-demo-ember-oak`, `sherpa-demo-lumen-bakehouse`), with source mirrored in `demo-stores/`. | Cleaner pull requests and a GitHub token scoped to just those repos. |
| 6 | 2026-10-22 | Next.js 15.5.28. | Earlier 15.5.x releases carry a published security advisory. |
| 7 | 2026-10-27 | Cloud Run services run in `us-east1`. Firestore (`sherpa` database) and the artifacts bucket stay in `us-central1`. | Cloud Run in `us-central1` rejected every deploy in this project, even a stock hello-world image ("Deletion in progress"), while `us-east1` deployed normally. |
| 8 | 2026-10-27 | JS SDK v6 is detected by `https://www.sandbox.paypal.com/web-sdk/v6/core` (or the live host); legacy v5 by `paypal.com/sdk/js?`. | Matches the current JS SDK v6 setup docs. |
| 9 | 2026-10-27 | The shopper never sends sandbox credentials to the model. Sherpa detects PayPal's login page and fills the sandbox buyer itself, masking those fields in screenshots. | Keeps credentials out of prompts, logs and stored screenshots. |
| 10 | 2026-10-27 | Payment confirmations from the computer-use safety system are acknowledged only while the active page is on the allowlist (the store, its preview or PayPal). Anything else stops the run. | Sherpa only ever shops its own sandbox stores with a sandbox buyer; everything else is refused. |
| 11 | 2026-10-27 | Screenshots are stored in Cloud Storage and served through the authenticated agent API, not a public bucket. | Keeps evidence private to the console. |
| 12 | 2026-10-27 | Health checks use `/health` (with `/healthz` kept for local use). | Cloud Run's frontend intercepts `/healthz` and returns its own 404. |
| 13 | 2026-10-27 | The fixer edits through `apply_patch` (exact, unique string replacement) and `write_file`, not unified diffs. | Exact replacements fail loudly instead of applying fuzzily, which keeps edits predictable. |
| 14 | 2026-10-27 | The fixer must pass a build and Sherpa's own static acceptance checks before `finish` is accepted; up to three rejections are fed back to the model. | Turns the planted-flaw list into a hard gate rather than a hope. |
| 15 | 2026-10-27 | Screenshots in pull requests use HMAC-signed, read-only links served by the agent (`/public/artifacts/...?...sig=`). | GitHub needs a public image URL; this avoids a public bucket. |
| 16 | 2026-10-27 | The Cart API contract was checked against PayPal's Cart API schema as implemented in PayPal's official WooCommerce plugin (`woocommerce-paypal-payments`, `ppcp-store-sync`), because the Store Sync pages linked from the hackathon brief now return 404. The contract lives in `services/agent/sherpa/agentready/cart_api.md`. | Field names (`validation_issues` with `code`/`type`/`context`/`resolution_options`, `payment_method.token` as the Orders v2 id, `checkout_fields` such as `DELIVERY_DATE_PREFERENCE`) follow that schema. Caller authentication (PayPal-issued JWT) is out of scope for the sandbox demo. |
| 17 | 2026-10-27 | The PayPal Agent Toolkit (`paypal-agent-toolkit` 1.11.0) is installed with `--no-deps`; Sherpa uses only its framework-neutral `shared.api.PayPalAPI` Orders actions in sandbox mode. | The package pins LangChain, CrewAI and OpenAI Agents SDK versions that Sherpa does not use. |
| 18 | 2026-10-27 | Agent-ready changes are a second commit on the same PR branch, followed by a redeploy of the same preview tag. | One PR tells the whole story; the commits keep checkout fixes and agent-ready work separate. |
| 19 | 2026-10-27 | Demo store services run with `--max-instances 1`. | Demo carts live in memory. |
| 20 | 2026-10-28 | The computer-use shopper and the buyer agent run with `thinking_level=LOW`; the fixer keeps `HIGH` with a 45-minute budget. | Measured on Vertex: about 2 s per call at LOW versus about 12–30 s otherwise. Clicking through a checkout needs little deliberation, while code changes benefit from deeper reasoning. |
| 21 | 2026-10-28 | The sandbox app is tied to a US business account and the test buyer is a US personal account. | A Nigeria-region sandbox merchant returned `PAYEE_ACCOUNT_LOCKED_OR_CLOSED`, and Venmo and Pay Later are US-only. |
| 22 | 2026-10-28 | Sherpa signs the sandbox buyer in itself, handling both PayPal entry pages ("Check out as a guest" with a Log In link, or the direct login form) and targeting only visible inputs. | PayPal varies the first page and keeps hidden duplicate inputs; credentials never go to the model. |
